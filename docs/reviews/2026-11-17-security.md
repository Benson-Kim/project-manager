# Attribute 1: Security

## 1. Executive Summary

### Security rating: **5/10 - Sound signed-document design and parameterised data access, but one path bug locks every PC out of an enforcing build and the trial and admin surfaces have no abuse controls**

Security here means:

- Only a genuine signed licence unlocks writes, and only on the machine it was issued for.
- The licence service cannot be abused to spam email, burn trials or mint licences.
- To-do alert pushes reach only people allowed to see the to-do.
- Shipped installers are always signed, and no secret leaks through the build.

The design is sound. Licences are Ed25519-signed documents checked against a key-id map (`Object.hasOwn`, no prototype lookup). Server actions and file routes are write-gated in one place. Every SQL Server proc takes parameters. The Worker has no npm runtime dependencies.

The weakness is everything around that core. The machine id is never read (DC-1), so a build that enforces licensing locks out every PC. Trial start is limited only per email address, which lets anyone lock out a stranger's trial and send them mail (LS-1, AU-1). One static admin token reads testers and mints licences with no scope, throttle or audit trail (AU-2). The release job publishes an unsigned installer if the signing settings go missing (CS-1). CI never scans for secrets (SC-1).

# 3. Detailed Findings

## SEC-01 - Critical: an enforcing build never reads the machine id

### Evidence

`electron/licence/machine-id.ts:18` passes `"HKLM\SOFTWARE\Microsoft\Cryptography"`. In a JS string the unescaped backslashes drop out, giving `HKLMSOFTWAREMicrosoftCryptography`. `reg.exe` fails and `readMachineHash` resolves null. `start.ts:64-68` then returns the closed state.

### Why it matters

No build enforces licensing today. The first one that does opens read-only on every PC, including paid ones.

### Recommended remediation

```ts
const KEY = String.raw`HKLM\SOFTWARE\Microsoft\Cryptography`;
```

Add a start-up log line when the hash is null.

### Tests

- Unit test: the argument passed to `reg.exe` equals `HKLM\SOFTWARE\Microsoft\Cryptography`.
- Unit test: a null machine hash under enforcement is logged and reported, not silently closed.

## SEC-02 - High: unsigned installer still published

### Evidence

- `desktop-release.yml:87-90` only warns when no signing variable is set.
- `verify-signature.mjs:59-61` exits 0 when `PM_PUBLISHER` is empty.
- `signing.cjs:121-135` returns `signed:false` and carries on.

### Why it matters

If the environment secrets or variables are lost, the next develop merge publishes an unsigned `--latest` release. Signed installs then auto-update to it.

### Recommended remediation

Fail the job when signing is not configured on the release branch, and make `verify-signature.mjs` exit 1 on an empty publisher.

### Tests

A script test that `verify-signature.mjs` with an empty publisher exits non-zero.

## SEC-03 - High: trial start limited only per email

### Evidence

`service.ts:64-78` and `handler.ts:101-106` key the start bucket on the email in the request.

### Why it matters

Anyone can use up a stranger's trial attempts, which locks them out, and can make the service send them mail. The attacker pays nothing; the owner pays Resend.

### Recommended remediation

Key the limit on (email, machine) and add a per-IP bucket. Send at most one mail per address per window.

### Tests

Worker test: many starts for one email from different machines leave a new machine able to start; a per-IP flood gets 429.

## SEC-04 - High: shipped packages carry known advisories

### Evidence

npm audit reports 33 advisories. The shipped ones: electron 44.7.0 (fixed 44.9.1), zod 4.6.5 (fixed 4.6.6), sanitize-html 2.18.0 (fixed 2.18.2, exact pin). undici 7.30.0 is dev-only.

### Why it matters

Electron and sanitize-html are on the path from content to screen.

### Recommended remediation

Bump the three; regenerate the lockfile with `npx npm@10 install --package-lock-only`.

### Tests

The production audit in `security.yml` (`npm audit --omit=dev --audit-level=high`) already guards this; also run it on pull requests.

## SEC-05 - High: no secret scanning in any pipeline

### Evidence

`security.yml` names its job "CodeQL & Secret Scan" but runs CodeQL only, weekly. No gitleaks or trufflehog step exists, and there is no `.gitleaks.toml` or pre-commit hook. A local gitleaks 8.30.1 run on this range was clean.

### Why it matters

Secrets in this repo include the signing key and the admin token. A leaked secret would go unnoticed until someone used it.

### Recommended remediation

Add a gitleaks step on push and pull request with a `.gitleaks.toml` allow-list for the throwaway e2e secret.

### Tests

The CI step itself; check it with one known-fake pattern generated at run time, never stored on disk.

## SEC-06 - Medium: push deliveries skip the to-do access check

### Evidence

`usp_TodoAlert_ListPushDeliveries.sql:36-40` joins subscription to alert without the to-do access predicate that the list procs use.

### Why it matters

A member who lost access to a to-do still gets its title in push notifications.

### Recommended remediation

Join the same access check the to-do list proc uses.

### Tests

A proc test: a subscriber without access gets no delivery row.

## SEC-07 - Medium: one static admin token

### Evidence

`handler.ts:140-170` checks one `ADMIN_TOKEN` for length ≥32 only. The same token reads testers and mints full licences. Failed attempts are not limited or logged.

### Why it matters

If the token leaks, an attacker can mint licences and read tester emails, and nothing records it.

### Recommended remediation

Separate read and mint scopes, rate-limit failed attempts per IP, and record every admin action in an append-only D1 `admin_event` table. Document how to rotate the token.

### Tests

Worker tests: a wrong token gets 401 and is counted; the 11th failure in a window gets 429; mint writes an `admin_event` row.

## SEC-08 - Medium: concurrent redeem binds one code twice

### Evidence

`service.ts:143-151` reads the code, then `d1-store.ts:96-100` upserts with `ON CONFLICT(licence_id) DO UPDATE SET machine_hash`.

### Why it matters

Two machines redeeming at once both succeed; the second silently re-binds the licence.

### Recommended remediation

Make the bind a single conditional update (`WHERE machine_hash IS NULL OR machine_hash = ?`) and check rows changed. The same pattern closes RC-4 (one trial per email) with a partial unique index.

### Tests

Worker test: two parallel redeems, exactly one succeeds.

## SEC-09 - Medium: placeholder keys with no build guard

### Evidence

`keys.ts` ships empty public keys and an empty service URL.

### Why it matters

An enforcing build made with these can never verify a licence.

### Recommended remediation

Read both from release settings at build time, and fail an enforcing build when either is missing.

### Tests

A build-script test: enforcement on with an empty key fails.

## SEC-10 - Medium: free update limit only displayed

### Evidence

`updatesUntil` is signed (`service.ts:214`), but nothing in the updater compares it with the release date.

### Why it matters

Free installs keep taking every update.

### Recommended remediation

Before downloading an update, compare its release date with `updatesUntil`.

### Tests

An updater unit test: a release after `updatesUntil` is not offered.

## SEC-11 to SEC-14 - Medium

- **SEC-11 (TM-1):** the Worker logs no 401, 429 or admin event. Fix: structured log lines for each.
- **SEC-12 (SC-2, SC-4):** `.gitignore` lacks `wrangler.toml`, `.dev.vars` and `.wrangler/`, but the README says they are never committed. The deploy runs unpinned `npx wrangler`. Fix: ignore the files and pin wrangler.
- **SEC-13 (SC-5):** `backup.yml:23,45,57,68,75` falls back to a literal SA password. Fix: fail when the secret is missing.
- **SEC-14 (SC-6, CS-3, AU-7):** `desktop-release.yml:68-85` gives the Entra client secret and the CSC password to the whole `electron:build` step. Fix: pass them only to the signing hook.

# 4. Component reviews

- **Auth and tokens:** strong signing and key-id lookup. Weak: no audience or issuer (AU-5) and a static admin token (SEC-07).
- **Authorization and tenancy:** writes are gated in one place. The push read path misses its access check (SEC-06).
- **Web:** the admin pages set a CSP, the main app does not (IU-1).
- **Mobile:** none in scope.
- **Input:** every proc takes parameters and Zod parses the edges. Bodies are not strict (EP-2) and priority is not checked against the managed list (FT-2).
- **Secrets:** stored in environments, but exposed too widely in builds (SEC-14) and never scanned (SEC-05).

# 5. Strengths Worth Preserving

- Ed25519 signed documents, key id checked with `Object.hasOwn`.
- One write gate: `action()` with the `licence:"read"` marker, and `fileRoute` write gating.
- Parameterised SQL Server procs throughout.
- No npm runtime dependencies in the Worker.
- Actions pinned to commit SHAs in every workflow.
- Signing secrets limited to the develop environment.

# 6. Prioritized Roadmap

- **Now:** SEC-01, SEC-06, SEC-08, SEC-09, SEC-10 (in the current fix list); SEC-02; SEC-04.
- **Next:** SEC-03, SEC-05, SEC-07, SEC-11, SEC-12.
- **Later:** SEC-13, SEC-14, then the Lows.

# 7. Recommended Tests

- Licence client: registry path argument; null hash under enforcement; enforcing build fails with empty key or URL.
- Worker: parallel redeem; per-IP trial limit; admin 401/429 and audit row; one trial per email under a race.
- Procs: push delivery honours to-do access.
- Updater: no update past `updatesUntil`.
- Release: `verify-signature.mjs` exits non-zero on an empty publisher.

# 8. Final Verdict

Safe to ship as it is today, because no build enforces licensing. **Do not ship an enforcing build** until SEC-01, SEC-02 and SEC-09 are fixed, and fix SEC-03 and SEC-07 before inviting public testers.
